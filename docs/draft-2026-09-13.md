## Problema

CodexBar muestra el porcentaje de consumo de las suscripciones de IA. Ese dato
tiene que estar siempre a la vista. Pero CodexBar ocupa memoria todo el tiempo
y depende de un proveedor externo para agregar funciones.

El trabajo diario ocurre en la terminal (Claude Code, Codex). El dato puede
vivir ahí, en un proceso que no queda corriendo.

| CodexBar 0.60.1 | 116 MB | Ya es Swift nativo. Consulta cada 5 min. |

Entorno: Go 1.26.4 instalado. Rust no. tmux 3.6a instalado, sin uso. Claude
Code sin status line configurada.

## Tradeoff a tener presente

- CodexBar ya es nativo y open source (`steipete/CodexBar`). Una app nativa
  propia ahorraría solo ~75 MB.
- **Mejora sin código:** desactivar el proveedor Antigravity en CodexBar
  ahorra 134 MB.
- El argumento para construir no es la memoria de una app nativa. Es **0 MB en
  reposo** con una herramienta de terminal, más funciones propias.

## Arquitectura propuesta

Separar la consulta de la visualización. La status line de Claude Code se
ejecuta muy seguido: nunca debe llamar a la red.

```
launchd (cada 5 min) ──► riserva fetch ──► ~/.cache/riserva.json ──► riserva line (lee cache, <5 ms)
   el proceso vive <1 s      (red)                                          │
                                                   ┌────────────────────────┼──────────────────┐
                                           status line de           status-right          riserva
                                           Claude Code              de tmux (opcional)    (TUI bajo demanda)
```

- **Dónde se ve:** status line de Claude Code (principal). tmux solo si se
  empieza a usar. Ghostty no tiene barra de estado programable.
- **Fuera de la terminal:** el job de `launchd` manda una notificación de macOS
  al pasar un umbral (80%, 95%).
- **Lenguaje:** Go. Es pegamento de I/O (HTTP, JSON, archivos). Bubble Tea +
  Lip Gloss para la TUI.

## Patrón común con `dictate` y `vinile`

Núcleo + CLI con salida `--json` estable. TUI y MCP son adaptadores finos
encima. Son repos separados. Si aparece código repetido (config, cache,
render), evaluar un módulo Go compartido recién entonces.

## Obtener el dato: el punto difícil

| Dato | Fuente | Confiabilidad |
|---|---|---|
| Tokens consumidos | Logs locales: `~/.claude/projects`, `~/.codex/sessions` | Alta |
| **Porcentaje del plan** | Endpoints OAuth internos y salida de las CLIs | Baja: no hay API pública. Cambian sin aviso. |

Leer cómo lo resuelve CodexBar y portar solo los proveedores que se usan.
Cuando un endpoint cambie, el arreglo es propio. Hoy lo hace el autor de
CodexBar, gratis.

## Riesgos

- Endpoints internos que cambian: el mantenimiento pasa a ser propio.
- Credenciales OAuth: leerlas del lugar donde cada CLI las guarda. No
  copiarlas a otro archivo.

## Fases

1. **Spike:** leer el porcentaje del plan de Claude y de Codex desde Go.
2. **v1:** `fetch` + cache + `line` en la status line de Claude Code.
3. Notificaciones por umbral.
4. TUI con detalle e historial. MCP solo si un cliente sin shell lo necesita.

## Decisiones abiertas

1. **Proveedores de la v1:** ¿Claude y Codex? ¿También Cursor, Grok,
   Antigravity?
2. **¿Qué se muestra en la línea?** Porcentaje, reset de la ventana, costo.
3. **¿MCP hace falta?** Los agentes con shell pueden ejecutar
   `riserva --json`.
4. **¿Se apaga CodexBar al tener la v1**, o conviven un tiempo?
